# STM32 Bare-Metal Interactive UART Terminal

An interactive line terminal for the STM32F4, built entirely with **register-level (bare-metal) programming in C**. A PC terminal sends a key over USART2, the STM32 acts on it, and the board prints feedback back to the terminal, using both the **TX** and **RX** paths of the USART.

> **This is my first bare-metal project.** I built it to learn how a microcontroller works below the level of any vendor library.

**No HAL is used anywhere in this project.** Every peripheral (RCC, GPIO, USART) is configured by reading and writing registers directly. The only vendor file included is the CMSIS device header (`stm32f4xx.h`), which provides register names and bit definitions.

---

## What it does

1. On startup, the board prints a banner and a prompt to the terminal.
2. You press a key on your keyboard (RX: PC to STM32).
3. If the key is `1`, the on-board LED turns **ON**. Any other key turns it **OFF**.
4. The board echoes the key and prints the LED state (TX: STM32 to PC), then shows the prompt again.

### Sample session

```
=== STM32 LED Terminal ===
Press '1' = LED ON, any other key = LED OFF > 1
LED is ON

Press '1' = LED ON, any other key = LED OFF > x
LED is OFF
```

| Clock | 16 MHz internal oscillator (HSI), default after reset |

| Terminal program | [PuTTY / Tera Term / other] at 115200 baud, 8N1 |

### Pin and peripheral map

| Function | Pin | Alternate function | Peripheral |
|---|---|---|---|
| UART TX | PA2 | AF7 | USART2 |
| UART RX | PA3 | AF7 | USART2 |
| LED | PA5 | n/a (GPIO output) | GPIOA |

USART2 is connected to the board's ST-Link, which exposes it to the PC as a **Virtual COM Port** over the same USB cable used for programming.

## How it works

**Data path:** keyboard, terminal program, USB, ST-Link Virtual COM Port, PA3 (RX), USART2, my code. The reply travels the same path in reverse through PA2 (TX).

### UART initialisation (`uart.c`)
1. Enable the clocks for GPIOA (AHB1) and USART2 (APB1) in `RCC`, because peripherals are off after reset.
2. Set PA2 and PA3 to alternate-function mode in `GPIOA->MODER`.
3. Select AF7 for both pins in `GPIOA->AFR[0]` to route them to USART2.
4. Set the baud rate in `USART2->BRR`: 16 MHz / 115200 rounds to 139, giving roughly 0.1% baud error, which is within tolerance.
5. Enable the USART, transmitter and receiver in `USART2->CR1` (`UE`, `TE`, `RE`).

### Transmit
Wait until the **TXE** flag in `USART2->SR` shows the data register is empty, then write the byte to `USART2->DR`.

### Receive
Wait (polling) until the **RXNE** flag in `USART2->SR` is set, then read `USART2->DR`. Reading `DR` clears the flag.

### `printf` retargeting
`printf` is redirected to the UART by defining `__io_putchar()` in `uart.c`. STM32CubeIDE's `syscalls.c` provides `_write()`, which calls `__io_putchar()` for each character. That function is declared there as a weak symbol, so my definition is linked in and sends each character to USART2. Output is made unbuffered with `setvbuf(stdout, NULL, _IONBF, 0)` so the prompt appears immediately, even without a trailing newline.

### LED control (`led.c`)
PA5 is configured as a general-purpose output and driven through the `GPIOA->BSRR` register.

## Project structure

```
Core/
├── Inc/
│   ├── uart.h      # UART driver interface
│   └── led.h       # LED driver interface
└── Src/
    ├── main.c      # Interactive terminal logic
    ├── uart.c      # USART2 register-level driver + printf retarget
    ├── led.c       # GPIO LED driver
    ├── syscalls.c  # Generated by STM32CubeIDE (calls __io_putchar)
    └── sysmem.c    # Generated by STM32CubeIDE (heap)
```

## Build and run

1. Clone the repo and import it into STM32CubeIDE (File > Import > Existing Projects into Workspace).
2. Build and flash to the board.
3. Open a terminal on the board's COM port: **115200 baud, 8 data bits, no parity, 1 stop bit**.
4. Press the board's reset button after the terminal is open so you see the banner.
5. Press `1` to turn the LED on, or any other key to turn it off.

## What I learned

- Reading the **datasheet, reference manual and board user manual** to find the pin mappings, register layouts, bit positions and bus assignments, rather than relying on generated code.
- Programming peripherals purely through registers: RCC clock enables, GPIO mode and alternate-function selection, USART configuration.
- How UART framing works (start bit, 8 data bits LSB first, stop bit) and how baud rate is derived from the peripheral clock.
- Status-flag based I/O (`TXE`, `RXNE`) and why reading `DR` clears `RXNE`.
- Structuring embedded C into separate driver modules with header files.
- How `printf` is retargeted to hardware through newlib's `_write` and a weak `__io_putchar` symbol.

### Problems I hit and how I solved them
- **`printf` produced no output while waiting for input:** newlib buffers stdout until a newline, so my prompt (which had none) never left the buffer. Fixed by making stdout unbuffered.
- **Output appeared twice:** caused by terminal local echo and by Enter being read as an extra command. Fixed by disabling local echo and ignoring `\r` and `\n`.

## Limitations and next steps

- RX currently uses **polling**, so the CPU is blocked while waiting for a key.
- Planned: interrupt-driven RX with a ring buffer, multi-character commands (e.g. `LED ON`), timer-based LED blink, and then DMA and an RTOS.
